# 근거와 검토 가이드

Diátaxis 유형은 독자 경험을 정리하지만 사실의 정확성을 보장하지 않는다. 먼저 세계와 일치하는지 확인하고, 그 위에서 문서의 흐름을 판단한다.

## 원천과 주장

주요 기술 주장마다 다음을 작업 메모나 기존 evidence ledger에서 확인한다.

| 항목 | 확인 내용 |
| --- | --- |
| 주장 | 독자가 사실로 받아들일 최소 단위 |
| 상태 | `확인`, `추론`, `미확인` |
| 계층 | `intended`, `implemented`, `observed` |
| 출처 | 파일과 symbol/줄, 공식 문서, 스키마, 테스트, 실행 결과 |
| 적용 범위 | revision, 제품 버전, 환경, 시간 범위 |
| 충돌 | 다른 계층이나 revision과 다른 내용 |

원천은 질문에 가장 가까운 직접 증거부터 확인한다.

- 의도: 승인된 제품 문서, ADR, 정책, 설계 기록
- 구현: 코드, 설정, API·데이터 스키마, 테스트, IaC와 CI
- 관찰: 재현 실행, 서비스 응답, 로그, 메트릭과 트레이스

각 계층은 다른 계층의 결손을 자동으로 채우지 않는다. 정적 호출 후보를 실제 런타임 경로라고 쓰지 않고, 오래된 문서의 의도를 현재 구현이라고 쓰지 않는다. 외부 자료는 공식·1차 출처와 적용 버전을 우선한다.

## 독자 근거와 프로필 충돌

독자에 관한 주장도 기술 주장처럼 근거의 강도를 구분한다. 독자의 명시적 진술, 인터뷰·관찰, 안전하게 집계된 사용 데이터와 승인된 역할 정의는 확인 근거가 될 수 있다. 작성자나 이해관계자의 의견, 직함에서 도출한 지식 수준과 저장소 문체에서 유추한 취향은 추론으로 남긴다.

프로필의 적용 범위와 마지막 검토일을 확인한다. 현재 요청이나 더 직접적인 근거와 충돌하면 이번 문서에는 현재 범위에 맞는 정보를 적용하고, 기존 프로필의 충돌과 갱신 후보를 보고한다. 한 번의 문서 작업에서 프로필을 자동으로 만들거나 조용히 갱신하지 않는다.

요청자의 전달 의도는 독자 근거가 아니다. 요청자가 원하는 반응과 독자가 안전하게 이해·행동하기 위해 필요한 정보가 충돌하면 사실, 위험과 대안을 보존한다.

## 역공학 산출물 연결

`docs/reverse-engineering/`이 있으면 필요한 범위만 읽는다.

1. `overview.md`에서 서비스 가치, actor, 용어, 구조와 분석 snapshot을 확인한다.
2. 관련 `scenarios/<slug>.md`에서 사용자 결과, 성공·실패·비동기 흐름과 신뢰 경계를 확인한다.
3. `evidence.md`에서 claim 상태, 계층, revision과 충돌을 대조한다.
4. 독자 문서에는 이해에 필요한 사실과 출처 관례만 반영하고 내부 분석 명령이나 원시 claim 표를 그대로 복사하지 않는다.
5. claim이 미확인이거나 현재 대상과 revision이 다르면 재검증하거나 제한으로 남긴다.

역공학 산출물이 없다고 새 Skill의 작업을 중단하지 않는다. 필요한 사실을 현재 자료에서 직접 확인하고, 범위가 서비스 재구성 수준으로 커지면 `reverse-engineer-service` 사용을 제안한다.

## 기존 문서의 보수적 변경

1. 문서의 현재 독자, 목적, 소유자가 관리하는 부분과 자동 생성 부분을 식별한다.
2. 유효한 인간 서술, frontmatter, 앵커, 링크, 예제 이름과 프로젝트 용어를 보존한다.
3. 목적과 충돌하는 부분만 이동·축약·분리하고 전체 문체를 불필요하게 다시 쓰지 않는다.
4. 사실이 충돌하면 기존 내용을 조용히 삭제하지 말고 적용 버전과 근거를 확인한다.
5. 분리한 문서의 대상 경로가 불명확하면 새 파일을 임의로 만들지 말고 변경 제안으로 남긴다.

리뷰 요청에서는 파일을 수정하지 않는다. 문제의 위치, 독자에게 미치는 영향, 근거와 가장 작은 수정 방향을 우선순위 순으로 보고한다.

## 실행 가능성 검증

튜토리얼과 방법 안내서의 명령은 문법 검토만으로 완료 처리하지 않는다.

- 격리된 로컬 또는 문서가 지정한 안전한 환경에서 성공 경로를 실행한다.
- 잘못된 전제조건, 잘못된 입력이나 예상 가능한 도구 오류 중 대표 실패 경로를 하나 이상 확인한다.
- 예상 출력은 안정적인 관찰 지점만 문서에 넣고 시간, ID, 절대 경로처럼 달라지는 값은 패턴으로 표현한다.
- 쓰기, 삭제, 배포, 비용 발생이나 운영 부하가 있는 검증은 사용자 권한과 승인 범위를 확인한다.
- 실행할 수 없으면 필요한 환경, 시도한 범위와 남은 위험을 보고한다.

참조 문서는 샘플 항목만 보지 말고 같은 범주의 항목이 모두 같은 구조를 따르는지 확인한다. 설명 문서는 사례가 원리를 실제로 지지하고 반례가 논지를 무너뜨리지 않는지 확인한다.

## 품질 검토

먼저 기능적 품질을 확인한다.

- 정확성: 원천과 일치하는가?
- 완전성: 목적 달성에 필요한 전제, 분기, 필드나 제약이 빠지지 않았는가?
- 일관성: 용어, 구조, 버전과 예제가 서로 충돌하지 않는가?
- 유용성: 문서 계약의 결과를 실제로 얻을 수 있는가?
- 정밀성: 확인된 사실과 추론·미확인을 구별하는가?

그다음 독자 경험을 판단한다.

- 필요한 내용이 예상 위치에 있고 시작점이 분명한가?
- 현재 목적과 다른 설명 때문에 흐름이 끊기지 않는가?
- 독자가 다음 행동이나 탐색 위치를 예측할 수 있는가?
- 성공, 실패와 완료를 스스로 판별할 수 있는가?
- 관련 문서로 이동해도 원래 맥락을 잃지 않는가?
- 주 독자의 실제 사용 순간과 먼저 가진 질문에 초점이 맞는가?
- 독자가 모르는 용어·단계·정신모형을 직함이나 취향만으로 생략하지 않았는가?
- 역할과 권한에 맞는 선택, 경고, 완료 조건을 제공하는가?
- 프로필의 확인·추론·미확인이 문서에서 과도한 확신으로 바뀌지 않았는가?

리뷰 결과는 심각한 사실 오류와 실행 위험, 목적·유형 충돌, 독자 부적합, 누락, 표현 개선 순으로 정리한다. 발견이 없으면 검토한 원천, 사용한 독자 근거와 실행하지 못한 범위를 명시한다. 실제 독자 테스트가 없으면 잘 읽힌다고 단정하지 않는다. 작성이나 재구성 결과에는 변경 파일, 선택한 문서 계약과 유형, 적용한 독자 프로필이나 가정, 검증한 명령, 남은 미확인 사항만 간결하게 보고한다.
