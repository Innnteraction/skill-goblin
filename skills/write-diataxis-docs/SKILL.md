# Write Diataxis Docs

한 번에 한 독자의 한 가지 필요를 해결한다. 네 유형의 문서 세트를 강제로 만들지 말고, 사실 검증과 독자 경험 설계를 서로 다른 문제로 다룬다.

## 시작

1. 요청이 새 문서 작성, 기존 문서 재구성, 검토 중 무엇인지 확인한다. 검토만 요청받았으면 파일을 수정하지 않는다.
2. 대상 저장소의 기존 문서 구조, 문체, 메타데이터, 링크와 출처 관례를 먼저 확인한다.
3. 코드, 설정, 스키마, 테스트, 제품 자료, 기존 문서와 역공학 산출물 중 사용할 수 있는 원천을 확인한다. 질문으로 확인할 수 있는 사실을 추측하지 않는다.
4. 다음 문장으로 문서 계약을 고정한다.

```text
이 문서는 [독자]가 [사용 순간]에 [원하는 결과]를 얻도록 돕는 [문서 유형]이다.
```

독자의 숙련도, 실행 환경, 잘못 수행했을 때의 위험과 성공 확인 방법도 필요한 만큼 기록한다. 입력이 부족해도 안전하게 진행할 수 있으면 명시적 가정으로 좁히고, 결과를 크게 바꿀 선택만 질문한다.

## 유형 결정

독자가 지금 필요로 하는 것이 행동인지 인지인지, 능력을 습득하는 중인지 적용하는 중인지 판별한다.

| 필요 | 습득 | 적용 |
| --- | --- | --- |
| 행동 | 튜토리얼 | 방법 안내서 |
| 인지 | 설명 | 참조 |

문서 유형을 선택하거나 혼합된 기존 문서를 재구성할 때 [문서 유형 가이드](references/document-types.md)를 읽는다. 문장 단위의 보조 내용은 허용하되 다른 사용자 필요가 독립된 흐름을 요구하면 별도 문서로 분리하고 링크한다. 폴더 네 개나 완전한 문서 세트를 먼저 만들지 않는다.

## 근거 구성

1. 문서의 주요 기술 주장을 원천과 대조하고 `확인`, `추론`, `미확인`으로 구분한다.
2. 의도, 구현, 관찰은 서로 대체하지 않는다. 문서와 코드가 다르면 현재 사실을 임의로 고르지 말고 적용 revision과 드리프트를 밝힌다.
3. `reverse-engineer-service` 산출물이 있으면 `overview.md`, `scenarios/`, `evidence.md`에서 관련 claim과 `intended`, `implemented`, `observed` 계층을 소비한다. 해당 Skill을 필수 선행 단계로 만들지 않는다.
4. 출처, revision, 검증 날짜와 claim ID는 대상 문서의 기존 관례에 맞춰 노출한다. 독자용 본문에 모든 내부 추적 정보를 강제로 삽입하지 않는다.
5. 근거가 부족하면 빈칸을 그럴듯한 사실로 채우지 말고 미확인 내용, 영향, 필요한 추가 자료를 보고한다.

근거 선택, 보수적 병합, 실행 검증이나 품질 리뷰가 필요하면 [근거와 검토 가이드](references/evidence-and-review.md)를 읽는다. 비밀값, 개인정보, 내부 업무 데이터는 문서나 검토 결과로 옮기지 않는다.

## 작성과 재구성

1. 독자가 가장 먼저 알아야 할 결과나 방향을 앞에 둔다.
2. 선택한 유형의 목적과 흐름에 맞춰 본문을 작성한다. 정보의 완전성을 이유로 다른 유형의 내용을 끼워 넣지 말고 필요한 문서로 연결한다.
3. 기존 문서는 인간이 작성한 의미, 유효한 링크, 메타데이터와 정보 구조를 보존하며 필요한 범위만 수정한다. 자동 생성 구역이 명확하지 않으면 전체를 재생성하지 않는다.
4. 상충하는 사용자 요구가 발견되면 현재 문서의 주된 목적을 유지하고, 분리할 내용과 연결 위치를 제안한다. 사용자가 함께 작성을 요청한 경우에만 추가 문서를 만든다.
5. 튜토리얼이나 명시적인 숙련 설계 요청에서만 예상 결과, 정상·흔한 실패·위험한 오판, 변형 연습, 단계적으로 줄어드는 힌트와 독립 수행 확인을 추가한다.
6. 기존 문서의 언어와 문체를 따른다. 새 한국어 문서는 정확하고 직접적인 표현을 사용하되 코드 식별자와 제품 고유명은 보존한다.

## 검증과 보고

1. 기술적 사실이 원천과 일치하고 적용 revision과 환경이 분명한지 확인한다.
2. 문서 계약 하나를 일관되게 해결하며 다른 유형의 흐름이 주된 목적을 방해하지 않는지 확인한다.
3. 튜토리얼과 방법 안내서의 명령은 안전한 범위에서 성공 경로와 대표 실패 경로를 실제로 실행한다. 실행할 수 없으면 이유와 미검증 범위를 명시한다.
4. 링크, 파일 경로, 예제 출력, 전제조건, 기본값과 완료 조건을 확인한다. 참조 문서는 항목 누락과 구조 일관성을 별도로 확인한다.
5. 작성·재구성에서는 변경한 문서와 검증 결과를 짧게 보고한다. 검토에서는 우선순위가 높은 발견부터 근거와 위치를 제시하고, 문제가 없으면 남은 검증 한계를 알린다.

완료 조건은 문장이 매끄러운지가 아니라 독자가 의도한 순간에 필요한 행동을 완료하거나 정보를 찾고, 결과를 스스로 확인할 수 있는지로 판단한다.
