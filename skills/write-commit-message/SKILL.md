# Git 커밋 메시지 작성

## 절차

1. Agent 지침, 기여 문서와 README, commit template·commitlint 설정, 최근 커밋 순으로 대상 프로젝트의 규약을 확인한다. 명시된 규칙을 과거 경향보다 우선하고, 충돌하는 규칙을 임의로 혼합하지 않는다.
2. `git status --short`와 staged diff를 확인해 변경 목적과 범위를 파악한다. staged 변경이 없으면 사용자가 지정한 diff나 설명을 근거로 삼았음을 밝힌다. 비밀값이나 개인정보를 메시지에 옮기지 않는다.
3. 독립적인 목적이 섞였으면 커밋 분리를 권한다. 하나의 커밋으로 작성할 때는 주된 의도를 기준으로 제목을 정한다.
4. 프로젝트가 정하지 않은 항목에는 [기본 컨벤션](references/convention.md)을 적용한다. 제목과 본문은 파일 목록보다 변경 의도와 결과를 설명하고, 오해하기 쉬운 개념만 짧게 풀어 쓴다.
5. Agent가 메시지를 생성하거나 실질적으로 초안을 작성했다면 UI나 실행 환경의 가장 구체적인 vendor와 model 식별자를 축약하지 않고 마지막 trailer에 기록한다. 제공되지 않은 식별자는 추측하지 않는다.
6. 메시지 작성·검토만 요청받았으면 커밋하지 않는다. 커밋 실행까지 명시적으로 요청받은 경우에만 프로젝트의 보안 검사와 staged diff 검토를 마친 뒤 실행한다.

## 출력

- 기본적으로 바로 사용할 수 있는 커밋 메시지만 Markdown 코드 블록으로 제시한다.
- 규약 충돌, 분리 필요성, staged 변경 부재는 메시지와 구분해 짧게 알린다.
